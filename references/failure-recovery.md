# 故障熔断机制

本文档定义所有故障场景的重试、降级、熔断规则。

---

## 重试规则

### 子 agent 调用失败

| 次数 | 间隔 | 动作 |
|------|------|------|
| 第 1 次 | 0s | 立即重试 |
| 第 2 次 | 5s | 等待后重试 |
| 第 3 次 | 15s | 等待后重试 |
| 3 次都失败 | — | 主 agent 降级执行 |

**降级执行**：主 agent 基于自身知识完成任务（如自行选方案而非搜索 GitHub）。降级结果仍走正常校验流程。

### 实验执行失败

| 场景 | 重试策略 |
|------|----------|
| 单个分支 OOM | 降低 batch_size 50% 重试，最多 2 次 |
| 单个分支崩溃 | 检查错误日志，修复后重试 1 次 |
| 所有分支失败 | 检查代码 bug，修 bug 后重新本轮 |

---

## 降级规则

### 并行降级

```
5 路并行（默认）
  → GPU > 85% → 减 1 路
  → 仍 OOM → 再减 1 路
  → 降到 1 路仍 OOM → 降级为 CPU 模式或减小模型
```

### 能力降级

| 能力 | 正常模式 | 降级模式 |
|------|----------|----------|
| 方案搜索 | 子 agent 搜索 GitHub | 主 agent 基于自身知识选方案 |
| 架构诊断 | 分析 loss 曲线 + 搜索文献 | 仅基于 loss 曲线判断 |
| 参数生成 | Optuna TPE（如有）→ 趋势分析 + 贝叶斯优化 | 扰动采样 → 随机采样（连续 3 轮无提升时回退） |
| 配置生成策略 | 按项目类型生成配置文件（见 `config-generation.md`） | 通用 fallback：命令行参数 > 配置文件 > 代码复制 |

**参数生成降级链**：
```
Optuna TPE（环境有 Optuna 时）
  → Optuna 检测失败 / Optuna 报错 → 回退到手动采样
  → 扰动采样（连续 3 轮无提升，最佳指标变化 < 0.005）→ 回退到随机采样
```

**Optuna 检测失败处理**：
- `python -c "import optuna"` 失败 → 记录到 `experiment/degradation_log.md`，使用手动采样
- Optuna 运行时报错 → 捕获异常，记录错误，降级到手动采样
- 不重试 Optuna 检测（环境没装就是没装）

## 熔断规则

### 质量熔断

**触发**：同一环节连续 3 次不达标。

**动作**（agent 自主决策，不询问用户）：
1. 第 1 次熔断 → 换调参策略重试
2. 第 2 次熔断 → 放宽达标标准（降低 5%-10%），记录到 decision_log.md
3. 第 3 次熔断 → 停止实验，生成报告说明目标过高

每次熔断事件记录到 `experiment/degradation_log.md`。

### 架构熔断

**触发**：3 种以上架构各调满 10 轮，最佳指标仍距目标 > 0.05。

**动作**：
1. 停止实验
2. 生成放弃报告
3. 分析原因（目标过高 / 数据问题 / 架构能力上限）

### 总量熔断

**触发**：跨所有架构累计 50 轮仍无突破。

**动作**：同架构熔断。

## 降级记录

所有降级事件记录到 `experiment/degradation_log.md`：

```markdown
## [时间] 降级事件

- **触发场景**：子 agent 搜索 GitHub 失败（3 次重试后）
- **降级动作**：主 agent 基于自身知识选方案
- **影响**：方案可能不如搜索到的方案精准
- **后续**：继续正常流程，结果仍走校验
```

## 故障处理流程图

```
故障发生
  ├── 可重试？ → 重试（按重试规则）
  │     ├── 成功 → 继续
  │     └── 仍失败 → 降级
  ├── 可降级？ → 降级执行
  │     ├── 结果合格 → 继续（记录降级事件）
  │     └── 结果不合格 → 熔断
  └── 不可重试/降级 → 熔断
        ├── 第1次 → 换策略重试
        ├── 第2次 → 放宽标准继续
        └── 第3次 → 停止，生成报告
```
