# Step 3：架构优化

**目的**：当调参触达架构瓶颈时，诊断瓶颈、搜索方案、修改架构、验证效果。
**前置**：Step 2 触发架构回溯条件（连续 10 轮无提升且距达标 > 0.03）。
**输出**：架构变更记录、更新后的代码、回到 Step 2 继续调参。

**本 Step 仅在架构回溯时触发**，不在每轮调参中执行。趋势分析、参数收敛检测、死循环检测等日常分析已在 Step 2 主循环中完成。

## 3.1 架构回溯流程

**触发条件**（由 Step 2 判断）：连续 10 轮无明显提升（< 0.01）且距达标仍有差距（> 0.03）

### 3.1.1 存档

当前最优代码、参数、完整历史 → `experiment/checkpoints/checkpoint-vN/`

### 3.1.2 诊断

从 `experiment/results.json` 提取 loss 数据，判断瓶颈类型：

1. 读取最近 5-10 轮的 `results.json`
2. 提取每轮的 `train_loss` 和 `val_loss`（如无 train_loss，仅用 val_loss + 指标趋势判断）
3. 绘制 loss 趋势（或对比表），对照下表判断瓶颈：

| 瓶颈类型 | 典型表现 | 判断方法 |
|----------|----------|----------|
| 过拟合 | train loss 降但 val loss 不降/升 | train_loss 持续下降 + val_loss 回升或持平 |
| 欠拟合 | train loss 和 val loss 都高 | 两者均高于 baseline 的 50% 以上 |
| 容量不足 | loss 停在高位不降 | 连续 5 轮 loss 变化 < 0.01 |
| 感受野不够 | 大目标好小目标差 | 分类别指标差异 > 0.15 |
| 梯度问题 | loss 震荡或突然 NaN | loss 标准差 > 均值的 30%，或出现 NaN/Inf |

**诊断优先级**：当多个条件同时满足时，按以下顺序判断：
1. 梯度问题（NaN/Inf 最优先，必须先解决）
2. 过拟合（train/val loss 分叉是明确信号）
3. 容量不足 vs 欠拟合：如果 loss 高且不降，先尝试增加容量（加通道/层数）。如果增加容量后仍不降，再判断为欠拟合（可能需要更多训练轮数或更好的优化策略）

### 3.1.3 多源搜索方案

spawn 研究子 agent（独立上下文，不污染主 agent context），搜索同类任务的解决方案。

搜索范围：论文、技术博客、框架文档、HF Hub、Stack Overflow、GitHub — 哪里有有用信息就去哪里搜。

搜索策略详见 `references/github-search.md`。

**子 agent prompt 模板**：
```
你是一个 [任务类型] 领域的研究助手。当前项目使用 [框架]，遇到了 [瓶颈类型] 问题。

请搜索以下来源，找出 2-3 个最相关的解决方案：
- GitHub：搜索关键词 "{task_type} improve {bottleneck_type} {framework}"，筛选星标 > 100 的项目
- arXiv/Google Scholar：搜索近期论文
- 技术博客/Stack Overflow：搜索实战经验

对每个方案，返回：
| 方案 | 来源 | 预期收益 | 风险 | 参考链接 |

要求：
- 方案必须与当前瓶颈直接相关
- 优先选"小改动大效果"的方案
- 最多返回 3 个方案
- 用中文输出
```

子 agent 返回结构化表格后，主 agent 结合自身分析，自我辩论选最优解。记录到 `experiment/decision_log.md`。

### 3.1.4 三层回溯框架

架构瓶颈不是只有"换模型"一种解法。把修改分为三层，便于归因：

```
优化策略层
→ loss、optimizer、scheduler、epoch、正则化（dropout/weight_decay/label smoothing）、梯度策略、学习率

数据策略层
→ augmentation、采样、归一化、patch 策略、label smoothing（也跨优化层，优先放此处）、train/val 划分

模型架构层
→ 通道数、层数、注意力、卷积核、backbone、感受野、残差连接、初始化
```

**回溯顺序**：
1. 先诊断瓶颈属于哪一层或多层。
2. 按"优化策略 → 数据策略 → 模型架构"的顺序尝试，同层内按成本从低到高。
3. 每次只改一个变量，并用原最佳超参做对照实验。

### 3.1.5 执行架构修改

**每次只能改一个变量**：一次回溯只做一项修改（例如只加 attention 层，或只换 loss 函数，或只改数据增强），否则后期无法归因指标提升来源。修改后**先固定超参跑一次对照实验**（使用 checkpoint 时的最佳超参），确认新 baseline 不低于旧架构的最佳指标，再进入 Step 2 粗搜。

**state.json 更新**：回到 Step 2 前写：
```json
{
  "phase": "tuning",
  "round": 0,
  "search_stage": "coarse",
  "next_action": "generate_configs",
  "architecture_version": "<新版本号>",
  "consecutive_no_improvement": 0,
  "retry_count": 0
}
```

**决策流程**：先按规则快速评估 → 规则不确定时再搜索 → 选最优方案执行。

```
诊断结论
  ↓
规则匹配（见下表）→ 有明确方案？
  ├── Yes → 评估成本/收益 → 执行修改
  └── No / 不确定 → 3.1.3 多源搜索 → 选最优方案 → 执行修改
```

**规则优先级**：规则匹配优先于多源搜索。只有当规则无法给出明确方案时，才启动子 agent 搜索。

**诊断→修改映射表**（按层和成本排序，优先选低成本方案）：

| 瓶颈类型 | 优化策略层（先试） | 数据策略层 | 模型架构层 |
|----------|-------------------|-----------|-----------|
| **过拟合** | 增大 weight_decay、加 dropout、提前停止 | 数据增强、mixup/cutmix | 减少模型容量 |
| **欠拟合** | 增加训练轮数、换更大学习率范围、换 optimizer | 简化增强、检查标注 | 增大隐藏维度、增加层数 |
| **容量不足** | 增加训练轮数、放宽 early stopping | — | 增大通道数（×1.5-2）、增加层数、添加注意力 |
| **感受野不够** | — | 多尺度输入/patch | 增大卷积核（3→5）、空洞卷积、多尺度分支 |
| **梯度问题** | 梯度裁剪、降低学习率、换 optimizer | — | 添加残差连接、BatchNorm、换激活函数/初始化 |
| **类别不平衡** | 加权 loss、Focal Loss | 重采样、过采样小类 | — |
| **小目标差** | — | patch 采样、复制粘贴增强 | 增大分辨率、FPN/多尺度 head |

**执行步骤**：
1. 从存档复制代码到工作目录
2. 按映射表选择方案（每次只改一个变量）
3. 用 Edit 工具修改代码/配置
4. 保留最优超参，先跑对照实验
5. 回到 Step 2 重新调参（沿用之前参数范围，从粗搜重新开始）

**记录**：每次修改写入 `experiment/decision_log.md`：选了哪一层、什么方案、为什么选这个、预期效果。

### 3.1.6 判定与回档

每次判定后**必须更新 state.json**：`phase` 不变（仍在 optimization 中），`next_action` 设为对应结果（回档则回 `generate_configs`，失败则回 `generate_report`）。

新架构在 Step 2 中调参，判定规则：
- 前 5 轮指标明显下滑（比 checkpoint 低 > 0.05）→ 提前回档
- 调满 10 轮更优 → 继续
- 调满 10 轮变差 → 记录失败原因后回档
- 调满 10 轮持平 → 再给 5 轮机会，或换下一层方案
- 所有方案无效 → 停止，跳 Step 4

每次回档写 `experiment/failed_architectures.md`：改了什么、为什么不行、教训。

## 上下文管理

Step 3 的多源搜索子 agent 返回结果后，若架构验证超过 5 轮，需压缩搜索结果详情：

- 子 agent 搜索结果：保留方案摘要表格，删除原始搜索输出
- 架构验证前 5 轮详情：保留完整
- 更早的验证轮次：压缩为"轮次 N：最佳指标=X，结论=Y"
- 压缩后读取 progress.md 恢复状态
